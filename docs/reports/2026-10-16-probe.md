## Orca

Command: `ORCA orchestration worker-start --help`
Observed: `[--agent <agent> | --terminal <handle>] ... [--model <id>] [--effort <level>] ...`
and `--model supports Claude, Codex, Cursor, Antigravity, and Muse opaque provider model ids; --effort requires --model ... Neither can combine with --terminal.`
Conclusion: model choice flag is `--model`; reasoning flag is `--effort`. No other model flag.

Command: `ORCA skills get orchestration --reference references/coordinator-loop.md`
Observed: `ORCA orchestration worker-start --task <task_id> --worktree current --agent claude --model opus --effort high --json`; "Pass it only when the user named a model; otherwise omit it"; "Compare `launch.requested` with `launch.effective`; never claim a model or effort from requested arguments alone."
Conclusion: the factory can pass `--model opus` or `--model sonnet`-style ids for Claude workers, and must read back `launch.effective`. Model ids are opaque provider ids; the exact id strings for Opus/Sonnet were not verified (only `opus` appears in the example).

Command: `ORCA orchestration worker-start --help | grep -i -E 'mcp|env'`, and grep of the orchestration guide and all seven references (`coordinator-loop`, `legacy-contract-migration`, `low-level-topology`, `messaging-and-gates`, `placement-and-remote`, `recovery-and-cleanup`, `worker-contract`) for mcp/env/persona.
Observed: no MCP or env option. The only "env" hits are `--environment` (a saved remote Orca runtime) and the word "environment" in prose.
Conclusion: a worker cannot be given an MCP server config or env vars at start. The spec's isolated chrome-devtools MCP under `xvfb-run` has to come from config the worker's Claude session reads itself (for example a per-job `.mcp.json` in the worktree launching the MCP through `xvfb-run -a`), or from the spawning terminal's inherited environment. Not tested here (no worker may be started). Spec §5.2 and §12 were edited accordingly.

Also observed: `worker-start` has no persona flag. Personas like `builder-p7` therefore have to be selected in the task spec text or by the agent's own config; to be settled in a later task.
